# 项目立项与组队

先区分简单任务与项目：一次交付且无需阶段协作的工作可以直接执行；用户明确要求项目管理时保留项目流程。不要因为群内没有其他 AI 就拒绝立项。

## 编制可审阅方案

从已有对话和材料提取目标、业务价值、期限、范围与本期不做的事。只询问会改变交付或授权的关键缺口；普通不确定项写成假设，避免反复补问。

每阶段写明交付物和可核验的完成条件。沿用用户指定的任务数、预算和日期，不把一篇文档机械拆成研发、测试等多个岗位任务。阶段验收只要求该阶段应交付的内容。

预算分别列 AI 用量、人力、外部费用，写明币种、依据和不确定性。没有计费数据时不要虚构单次调用价格；已上报费用不等于全部费用。预算方案不表示已经付款或聘用。

当前主角承担产品经理职责；按实际工作匹配最小团队。同一 AI 可兼岗，明确每人的职责、参与阶段、交付和退出条件。候选顺序：已加载角色 → HUB 中确实存在的角色 → 提议新建角色。不存在的角色不能填写成已加入；真人与供应商单独列建议。

## 与 Echo 项目流程衔接

在支持 Project OS 的对话中，`/project run <目标>` 进入立项流程，立项获批后建立计划；后续 `/project run` 请求阶段执行。命令必须由真实用户输入或产品提供的调用接口发起，不能把自己输出的命令当作执行结果。

方案获批与成员实际加载、入组分别核验。审批、权限、预算拦截由宿主执行；Skill 不能替用户批准，也不能修改数据库绕过。已有授权按其明确范围使用，不重复申请相同事项。

出现模型或工作区故障时，报告实际原因和停在哪一步，不归咎于人员不足，不冒充已立项成功。

新品发布项目可按需读取 [新品发布交付模板](references/product-launch.md)。

## 验证边界

本技能是人工整理的流程指导，不是已自动学习的成功案例。2026-09-11 实跑已验证 OpenCode/big-pickle 立项、审批和任务拆解；完整交付与验收尚未跑通。不要将此状态推广为所有引擎或业务已验证。
