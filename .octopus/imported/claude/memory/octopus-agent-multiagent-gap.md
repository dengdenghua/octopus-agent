**问题**:octopus 的 subagent/多代理协作框架跟 Claude Code(Agent+Workflow)差多少。三个 Explore 实证读码(都带 file:line)后的结论,**先证后断言**(本会话 gap 假设被推翻 6+ 次的教训)。

**octopus 不弱/更强的地方(原语层)**:
- 共享黑板 `bb_read/bb_write/bb_keys` 按 turn_id 共享(`blackboard.py`),lead+并行子代理同 turn 互读写——**Claude Code 没有**(子代理只能靠返回值+编排者传参)。
- 10 个内置 ephemeral 角色(researcher/critic/implementer/architect/arbiter…)各带 system_prompt+tool_allowlist+share_context/memory(`ephemeral_agents.py:91`);`.claude/agents/*.md` 自定义 agent 约定**与 Claude Code 同款**。
- per-agent 可观测:`subagent_spawned/finished` 带 codename/avatar/role/files_touched/duration → 工作台 tile。比 Claude Code /workflows 进度组更细。
- 注入污点继承(父→子 fail-closed,`bridge.py:348`)——Claude Code 框架没建模。
- 廉价模型档(`use_cheap_model→glm-4-flash`)。
- 治理真强制:并发槽 64(`OCTOPUS_MAX_ACTIVE_SUBAGENTS`,fail-closed)、每轮委派 5(smart-budget,首错免费)、单任务 20k token。

**真正的差距(Claude Code 领先)**:
1. **没有「确定性编排程序」层**(最大):octopus 编排只有①模型驱动(LLM 自吐多 tool call→`_dispatch_parallel_dispatch` ≤4,或 `call_agent_parallel` ≤8,模型临场决定)②固定配方(`TeamRunner` 顺序/evaluator-optimizer、`SwarmRuntime` 拓扑分层)。**没人能表达任意多代理控制流**(find→dedup→3-vote verify→loop-until-dry)。Claude Code 的 Workflow 是通用确定性编排 surface。
2. **并行是栅栏,无 pipeline 语义**:`call_agent_parallel` 用 `wait(ALL_COMPLETED)`(`delegation_skills.py:972`),等最慢的。Workflow 的 pipeline() 各 item 独立流水。
3. **无结构化输出 + 无投票/共识**(已补,见下):子代理返回自由文本 envelope,无 per-call schema 校验;聚合是「模型自己从 successes 综合」,**明确无多数表决**(Explore 实证)。
4. **不能安全并行写文件的 agent**:全进程内共享 cwd,靠串行化 write 工具避冲突;Claude Code 有 worktree 隔离。
5. **累计成本天花板没接**(只告警,`bridge.py:44` 自承)+ 编排级无 resume。

**已补:`call_agent_vote` 共识闸(commit `c31b6e6`,差距#3)** —— adversarial-verify/judge-panel 原语。spawn N 个独立投票者同题→各出 `VERDICT:`→多数表决(confidence+dissent)。复用 `_call_agent_parallel` 做 fan-out(并发/taint/预算/重试/超时全继承),纯聚合核心 `_extract_verdict`/`_tally_votes` 单测;n 夹 [2,5] 合每轮委派上限;平票/无判=诚实回 verdict=null + `[no-consensus]`/`[no-verdict]` note,不伪造决定。注册为第 3 个 delegation 技能(`register_delegation_skills` 返回 3,`arbiter` 是 `_INTERNAL_AGENTS` 不可直调故默认投票者用 `reviewer`)。13 测 + ruff 净(该文件 426/430/433 是既存基线、非我引入)。**典型用法**:`call_agent_parallel`(收候选)→`call_agent_vote`(裁决「这 bug 真的吗/补丁修好没」)。

**已补:opt-in 编排预算包络(commit `7109e9f`,差距#5 的 spawn-count 部分 + B 的前置)** —— 用户选"预算包络优先"。痛点:扁平 `_PER_TURN_ABSOLUTE_LIMIT=5`(按 spec 计,`delegation_budget.py`)让任何多阶段/循环编排跑不起来(同轮第 3 次 fan-out 的 pre-check 直接拒)。做法:`orchestration_budget_scope(K)` 上下文里把扁平 cap **替换**成单一有界总额(可跨阶段 spawn 至多 K,fail-closed 硬停);无 scope=原 5-cap 不变。**实现**:`OrchestrationBudget`(线程安全 charge)+ ContextVar scope;`check_absolute_cap`/`record_delegation` 加 `budget=` 参数,激活时充包络而非轮计数。**跨线程坑**:ContextVar 不传进 ThreadPool worker → `_call_agent_parallel` 在调用线程捕获包络、闭包传入 `_run_one` 的 per-spec record(单发 `_call_agent` 主线程直接读 ambient)。**opt-in+内部**:scope 由受信编排代码带 sane bound 进入,**不是模型 per-call 旋钮**(否则绕过 turn cap = 安全回退,例如 vote 刷量无限 spawn)。9 测。**注意**:补的是 spawn-count;cost/token 的 `TokenBudgetTracker`(`budget_tracker.py`,仅告警)仍未接硬停,另算。

**已补:`run_orchestration` 确定性编排执行器(commit `ca4bbd4`,差距#1 的核心)** —— 多代理 gap 三连收口的最后一块。模型声明 `goal`,recipe 在代码里跑**确定性多轮发现循环**:每轮 fan-out n 个 worker(`call_agent_parallel`)→`_split_findings`(按行拆,正则只剥真列表标记 bullet/`1.`/`(3)`+空格、**保留内容开头数字**如"3 retries"、per-worker 50 行上限)→`_dedupe_findings`(归一去重 vs 全部已见)→loop 直到 dry(连续空轮 > patience)或预算耗尽;可选 `verify=True` 对每条 finding 走 `call_agent_vote`(majority-drop 才丢)。**循环/去重/停止逻辑全在代码**(非模型),全程在 `orchestration_budget_scope(max_spawns)` 内有界——这才让「扁平 5/轮 cap 禁止的多轮循环」成为可能。**嵌套预算**:一次 orchestration 对外只记 1 次 turn cap(防刷),对内 fan-out/vote 走包络。clamp n[1-6]/rounds[1-5]/patience[0-3],max_spawns 自动估算上限 48。注册为第 4 个 delegation 技能(`register_delegation_skills`→4)。9 测(纯 helper + 多轮收集 + dry-stop + 跨轮去重 + verify-drop + 缺 goal + **真栈 budget-stop**:mock call_subagent 走真 `_call_agent_parallel`,max_spawns=4/n=3 → 第 3 轮无 room 停)。**这是本会话三件套的合体**:`call_agent_parallel`(fan-out)+`call_agent_vote`(验证闸)+ 预算包络(有界)= 真正对齐 Claude Code Workflow 的「loop-until-dry + adversarial-verify」范式。**后续打磨**:`59f4a57` `_split_findings` 正则只剥真列表标记(保内容数字)+ per-worker/总量上限(防失控 worker);`98e6819` `agent_id` 可传**角色列表轮转**(diverse-lens,multi-modal-sweep:researcher+explorer+critic 比 3×researcher 发现更多;`_coerce_roles` 去重/跳 None);`7f5989c` 把 `call_agent_vote`/`run_orchestration` 写进 `react_types.py` 技能目录(此前注册了但模式引导一次没提=注册≠被用)。**坑(多会话)**:本想也写进 `react_loop.py` swarm 引导,但该文件正被另一会话大重构(工作树 +288/−1309 拆 react_checkpointing/react_loop_controls),`git add` 会扫入整个外来 diff→撤回我那处,只提交干净的 react_types.py。`call_agent_vote`/`run_orchestration` 全栈整合测试见 `28f7506`。

**已补:确定性 worktree loop(commit `60d9c5f`,差距#4 的机器层)** —— octopus 此前**没有程序化 worktree 隔离**,只有 `vibecoding-general-swarm/SKILL.md` 用 **prompt 文字**叫 subagent 手动 shell `git worktree add`(非确定性)。新 `runtime/execution/subagents/worktree_loop.py`:`worktree_scope(repo,name)`(off HEAD 建隔离 worktree+新分支→yield (path,branch)→finally 必清 worktree+分支)+ `run_worktree_loop(repo, tasks, worker, max_workers)`(每任务自己 worktree 并发跑注入的 `worker(path,task)`→抓各自 `git diff --cached`→清理;**绝不 auto-merge**,返回 diff 给 lead/人审用;`git worktree add/remove` 加锁串行=动主 repo 注册表,worker+各 worktree 的 diff 抓取并发=各有独立 index)。worker 是**注入 callable**(机器与"跑什么"解耦),真 git repo 单测 5 条(隔离/出错必清/失败隔离/非 repo+空任务守卫)。ruff+import-direction+orphan ratchet 全绿。**works-today 消费者(commit `d049974`)**:`shell_worktree_worker(argv)` 在每个 worktree 内跑固定 argv(cwd=worktree),task 经 `$OCTOPUS_WORKTREE_TASK` 传入(不插值进 argv、不开 shell→untrusted task 不能注入)。→ run_worktree_loop 现在**端到端可用**(并行 codemod/格式化/构建于隔离 worktree),真 git+真 subprocess 测过。**subagent-as-worker 仍缓(诚实结论,非"并发重构"——那句我之前夸大了,已更正)**:实测 executor.py mtime≈14h 前(陈年未提交存量,非活跃会话;近 10 提交全我的),所以约束只是普通提交卫生(可 `git apply --cached` 隔离)。**真正的拦路是**:给单个 worker 设 cwd=worktree 要改 `resolve_write_scope(_sess)` + `_sess.metadata["workspace_path"]`(executor.py:477-482,`_sess`=`current_session()` contextvar)——这是 **ADR-002 安全写作用域核心**;worker 共享父 session 对象,per-worker 覆盖要么 mutate 共享 session(并发竞争)要么动这条安全路径。**且无真后端 live 验证**(跑不了真 subagent 看它是否真写进 worktree)。盲改安全写路径 + 半接线(透了 workspace_path 但 executor 不路由→文件静默写错地方)是最坏结果 → 故意不盲做,等能 live 验证时再接。当前 worker=任意 callable / shell worker 已足够可用。
