# Kimi Replay 过程挖掘与 Octopus 借鉴建议

> 目的：研究 Kimi Replay 案例页面的过程表达方式，提取可迁移的产品机制。本文明确区分“正常工作”和“案例回放”：回放只服务于案例展示、复盘和复用，不进入正常工作主流程。

## 一、观察到的 Kimi 过程

本次观察对象是 [Kimi Replay](https://www.kimi.com/replay/19e6ed51-6802-8cdb-8000-00008b6228c0)，并保存了录屏和关键帧。页面展示的是一个已经完成的案例，任务为生成 `200 篇文献知识图谱`。

Kimi 的过程可以还原为：

1. 明确任务目标和项目规格。
2. 按 `ITEM 1a / 1b / 2 / 3 / 4a / 4b / 5` 切分工作。
3. 阅读已有文件、检查项目结构。
4. 分批编辑和生成内容。
5. 发生编辑失败后，明确显示失败原因，重新阅读上下文，再次编辑。
6. 构建项目，发现语法错误。
7. 定位文件末尾的重复片段，修复后重新构建。
8. 部署并打开预览。
9. 用结果表逐项确认完成状态，并给出浏览器验收清单。
10. 交付预览地址，同时提供“预览 / 代码 / 做同款”等后续入口。

它展示的不是每一个内部 Agent，而是“目标—阶段—动作—纠错—验证—交付”的可读叙事。页面中没有暴露完整的子 Agent 拓扑，也没有把所有底层工具调用平铺给案例观众。

## 二、Kimi 最值得借鉴的五个机制

### 1. 用命名事项代替流水账

`ITEM` 编号让长任务有稳定的章节锚点。用户始终知道当前在解决哪一块，而不是面对连续滚动的工具日志。

可迁移为统一的 `阶段 / 事项 / 当前目标` 数据结构：每个事项都有标题、状态、当前动作和结果摘要。

### 2. 把失败变成过程的一部分

Kimi 明确展示“文件编辑失败”，随后说明“重新读取精确文本—找到锚点—再次编辑”。这比只显示最终成功更可信，也比原始堆叠错误日志更容易理解。

可迁移为面向用户的恢复状态：`失败原因 → 恢复动作 → 恢复结果`。底层命令和完整堆栈仍可放在展开详情中。

### 3. 每个阶段都有可验收结果

最终的 `Fix Report` 用 `Item / Status / Details` 汇总每一项，并附上 5 条浏览器检查项。它将“Agent 说做完了”变成“用户可以核对什么”。

可迁移为结果回执：完成事项、产物、验证方式、未完成事项和风险。

### 4. 结果优先于过程细节

案例页主体是可阅读的产物和预览，而不是 Agent 数量。过程说明服务于理解结果，结果本身占据视觉中心。

这只适用于案例回放和结果展示。正常工作仍需要实时状态、暂停、审批、错误处理和工作台控制。

### 5. 交付动作集中且明确

回放完成后，Kimi 在底部集中提供“回放完成 / 看回放 / 做同款”，同时保留“预览 / 代码 / 全屏预览”。用户不需要在长页面里寻找下一步。

Octopus 可以在案例页借鉴这种结果收口，但不应在正常执行页增加“回放”作为主动作。

## 三、与 Octopus 当前实现的映射

| Kimi 的表达 | Octopus 当前对应 | 差距 / 建议 |
| --- | --- | --- |
| 命名事项与阶段 | `ProcessTrace` 的阶段卡、`deriveAgentPhases` | 已有基础，但需要更稳定地显示“当前目标”和阶段结果，而不只是进度数值。 |
| 失败后的恢复链路 | `LiveToolTimeline` 和工具事件状态 | 有底层事件，但用户层缺少统一的“失败—恢复—结果”摘要。 |
| `Fix Report` | 右侧 `Agent 工作台` 的进展和上下文 | 工作台偏执行监控，缺少完成后的结果回执、验证清单和产物入口。 |
| 子 Agent 状态 | `Agent 集群`、右侧子智能体列表 | 正常工作中有价值；案例回放中应隐藏拓扑，只保留阶段性贡献摘要。 |
| 过程记录收拢 | 当前委派已聚合为 5 条角色摘要 | 方向正确。下一步应让摘要表达“做了什么 / 结果是什么”，不只是“多少条”。 |
| 预览、代码、复用 | 本地正常工作页与 REC 录制入口 | “预览 / 代码 / 做同款”应属于案例结果页；REC 负责生成案例资产，不应改变正常工作界面语义。 |

## 四、按优先级的建议

### P0：正常工作页补齐“目标—结果”两端

在当前 `ProcessTrace` 顶部增加一条简短的当前目标，例如“正在核对审计范围”，完成后替换为结果摘要。右侧工作台增加一个固定的“本轮结果”区，包含：完成事项、异常事项、产物链接、下一步建议。

这能直接改善当前页面的问题：即使委派已经从大量明细压缩为 5 条，用户仍可能只看到“204 条 / 114 条”，却不知道这些调用带来了什么结果。

### P1：统一事项级事件模型

为每个事项保存：`id`、`title`、`status`、`currentAction`、`summary`、`evidence`、`recovery`、`startedAt`、`finishedAt`。界面默认只渲染事项卡；工具调用、子 Agent 明细和日志进入可展开详情。

重点是让“聚合”有语义，而不只是数量聚合：例如“Code Reviewer：完成 204 次检查，发现 3 个高风险项，已交给修复阶段”。

### P1：把异常恢复做成可读链路

在正常工作页显示：`发现问题 → 正在重新检查 → 已修复 / 仍需人工处理`。错误详情保留在展开层。这样可以吸收 Kimi 的可信度设计，同时不让主界面变成日志墙。

### P2：单独设计案例回放页

案例回放页可以采用 Kimi 的内容优先结构：顶部任务标题，中部阶段叙事和产物，底部固定结果栏。建议固定显示：案例状态、关键阶段、最终产物、验证清单、预览、代码、做同款。

该页面读取已完成的回放资产，不连接正常执行中的实时控制状态；正常工作页不显示回放播放器、不自动进入回放、不把案例叙事混入当前任务。

### P2：录制产物标准化

REC 结束时保存一份可复用案例包：任务摘要、阶段事项、关键动作、异常恢复、产物、验证结果、截图 / 录屏和脱敏信息。回放页只消费这份案例包，以保证长期可用和可复盘。

## 五、不建议照搬的部分

- 不要把 Kimi 的长篇自然语言叙事直接塞进正常工作流；正常工作需要更高的信息密度和更强的控制性。
- 不要为了模仿 Kimi 增加“回放”按钮到正常任务主操作区；回放属于案例入口。
- 不要在案例页暴露所有子 Agent、内部队列和工具调用；这些内容适合诊断详情，不适合案例主叙事。
- 不要只复制视觉上的底部状态栏；如果没有事项状态、验证证据和产物链接，底部操作只是装饰。
- 不要把“完成”只定义为 Agent 停止运行；应区分执行完成、构建通过、部署成功和用户验收通过。

## 六、建议的产品边界

```text
正常工作
  实时执行 → 当前目标 → 进度 / 审批 / 异常恢复 → 结果回执
       └── 工作台：Agent、上下文、日志、控制

案例回放
  已完成案例 → 阶段叙事 → 关键纠错 → 产物预览 → 验证清单
       └── 看回放 / 预览 / 代码 / 做同款
```

结论：Octopus 当前最应该借鉴的不是 Kimi 的“回放形态”，而是它对过程的压缩方式——用命名事项组织复杂执行，用恢复链路解释失败，用验证清单证明完成，用结果回执收口。正常工作与案例回放应保持两套清晰、互不混淆的界面语义。
