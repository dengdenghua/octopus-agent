## 1. 结论

**现在不可发布。** 最该先修的是 `runtime/memory/threads/store.py:990`：
`update_state` 每次都整文件 `read_text()` 重读线程日志，把每轮写入变成 O(n²)。
实测第 200 轮 71.85ms vs HEAD 4.87ms（14.8×，且持续拉大），而 `self._lock`
是**进程级单把 RLock**，所以一个长会话会拖慢同进程内所有线程。

其次是一个方法论问题，比任何单条 bug 影响更大：这个分支的"生产就绪"门禁
**不是行为验证，是源码/文档子串 grep**。我用 5 个只含关键词列表、零实现的
stub 文件让 `compute_ecosystem_readiness()` 返回 `ready: True, score: 1.0, 10/10`。
在修完下面的 P1 之前，不要用这套门禁的绿灯作为发布依据。

## 3. P1 问题

### P1-1 ThreadStore 每轮整文件重读 → O(n²)，且进程级锁放大

**位置** `runtime/memory/threads/store.py:990`（配合 `_state_mutation_lock.py:127`）

**什么坏了** `update_state` 内调 `latest_persisted_thread()`，其实现是
`path.read_text().splitlines()` 后 `for line in reversed(lines)`——整文件读。
日志随轮次单调增长，于是第 N 轮要读 N 轮历史。HEAD 的 `update_state`
（旧 448 行）只有 `_deepcopy(self._threads[thread_id])`，无文件读。

**证据**（我独立跑的基准，非代理转述）

| turn | 工作树 ms | HEAD ms |
|---|---|---|
| 1 | 0.98 | 0.47 |
| 50 | 5.45 | 1.57 |
| 100 | 17.77 | 2.58 |
| 150 | 52.51 | 3.81 |
| 200 | **71.85** | **4.87** |

HEAD 线性，工作树二次。验证代理用更小 payload 独立复现同一曲线（122ms vs 8.2ms）。

**影响** `self._lock = threading.RLock()`（`store.py:191`）是每 store 一把且
**跨越整个文件读**持有，所以 per-thread 的 `thread_mutation_lock` 不构成隔离：
一个 38MB 的大会话会阻塞同进程内其它线程的小更新。长会话越用越卡，且是全局的。

**修复方向** 让 `update_state` 走内存态（恢复 HEAD 的 `self._threads` 读法），
或把 `latest_persisted_thread` 换成尾部增量读（seek 末尾反向扫描），并把文件 I/O
移出 `self._lock` 的持有区间。

### P1-2 就绪度/认证门禁是子串 grep，可被注释满足

**位置** `runtime/safety/evolution/ecosystem_readiness.py`（`_topic_status`）、
`browser_desktop_quality.py:314`，共 **11 个模块 / 105 条 `required_terms`**，
其中 8 个模块被 `scripts/production_readiness_gate.py` 直接 import。

**什么坏了** 判定核心是
`path.exists() and term.lower() in path.read_text().lower()`。分数 =
命中条数/总条数。`browser_desktop_quality.py:314` 更松：先把多个文件 join
再匹配，任一文件命中即算过。

**证据** 我给 10 个 topic 只写 5 个 stub 文件（内容仅一行关键词列表，零实现）：

```
ready : True | score: 1.0 | passed: 10 / 10
```

`ecosystem_readiness` 的 10 条里 **7 条 grep 的是文档散文**
（`docs/guide/operator-readiness.md`）——文档写了 "sandbox"/"override"
就算权限就绪。

**影响** 这是发布放行依据。它衡量的是"关键词写没写"，不是"功能对不对"，
且方向可逆：见 P1-3。

**修复方向** 把 `required_terms` 降级为"文档存在性提示"，不参与 `ready`；
真正的 ready 应挂到已有的行为测试（`tests/test_plugin_registry.py` 这类）
的实际执行结果上。

### P1-3 权限规则覆盖门禁读机器本地状态，干净检出必红

**位置** `runtime/safety/evolution/permission_sandbox_quality.py:227`
（`ready: bool(drafts) and verified == len(drafts)`）

**什么坏了** 两个原因叠加。
其一，插件来源是 `base/.octopus/plugins/codex`，本机 35 个目录里
**只有 2 个在 HEAD**（product-design、remotion），其余 33 个
（github/slack/stripe/figma…）是本地安装的第三方插件，本就不该提交。
其二，HEAD 里那 2 个插件**根本没声明 permissions**，
且 `policy_review_rules.py:326` 会把 `ui:` 前缀过滤掉，于是 0 drafts；
而 `ready` 要求 `bool(drafts)` 为真——"没有东西需要规则"和"规则缺失"不可区分。

**证据**

```
本机工作树          : ready: True  | plugin_count: 35 | 27/27 verified
git archive HEAD    : ready: False | plugin_count: 2  | 0/0
```

**影响** 门禁在开发机上假绿、在 CI/发布机上真红，且红的原因不是缺陷。
和 P2-1 是同一类"未跟踪状态渗入判定"，但方向相反（这里本地状态制造假绿）。

**修复方向** `_plugin_policy_coverage` 把"无可执行权限"当作**平凡覆盖**
（`ready = verified == len(drafts)`，去掉 `bool(drafts)`），并把插件来源
显式限定为仓库内跟踪的集合。

### P1-4 未跟踪模块导致 paper_trading 在发布产物中直接 ImportError

**位置** `runtime/platform/plugins/bundled/paper_trading/__init__.py:53,55`

**什么坏了** 已跟踪的 `__init__.py`（工作树版）`from .quote_hub import ...`、
`from .signin import ...`，但 `quote_hub.py` / `quote_service.py` / `signin.py` /
`page/watch.js` **四个文件都未跟踪**。HEAD 自身是自洽的（HEAD 的 `__init__.py`
不 import 它们），所以现在还没炸——但只提交已跟踪改动就会炸。

**证据** 我把工作树的 `__init__.py` 覆盖到 `git archive HEAD` 上模拟"只提交
已跟踪文件"：

```
ImportError: cannot import name '_CheckInRequest' from
'...paper_trading._http_support'
```

`tests/test_packaging_include.py::test_release_critical_new_files_are_tracked`
正是为此设的哨兵，它现在红着，是**正确告警**。

**影响** 一旦按当前工作树提交，`paper_trading` 插件在 wheel/`git archive`
产物里 import 即失败。

**修复方向** `git add` 那四个文件（连同 `_http_support.py` 的配套改动）
一并提交；不要单独提交 `__init__.py`。

## 4. P2 问题

### P2-1 12 个测试依赖未跟踪的机器本地状态

`tests/test_agents_router.py:1195` 断言 `status == "detected"` 却得到
`"registered"`。根因：`agents_local_partner.py:377`
`registered = in_registry or dir_registered(agent_id)`，而 `dir_registered()`
读**真实** `agents/` 目录。本机有未跟踪的 `agents/local_trae_cli/profile.jsonc`
（真实注册产物）。测试 mock 了 `_which_local_partner_command` 和
`subprocess.run`，却没隔离 `default_agents_root()`。

证据：把 agents root 指向空目录后同一测试 `1 passed`。
`tests/conftest.py` 无 `AGENTS_ROOT` 相关 autouse fixture。

影响：CI（干净克隆）会过，任何注册过本地 CLI 的开发机会红——正好和 P1-3 相反。
修复：给这类测试加 `monkeypatch` 隔离 `default_agents_root`，最好做成 autouse fixture。

### P2-2 reasoning 模型 max_tokens 地板在 entry 路由分支失效

`runtime/sensing/model_router/openai_router.py:425-429`。原逻辑是
`model_is_reasoning or model_supports_thinking` 的 OR 判断，entry-bound 分支
只保留了 `supports_thinking` 一半。实测 `deepseek-r1` 在 entry 缺
`supports_thinking` 键时 `max_tokens` 从 256 掉到 64。

网关不救场：`stream_handler.py:182` 用的是 `model_supports_thinking`，
与 `model_is_reasoning` 在 `deepseek-r1`/`kimi-k3`/`glm-5.1` 上正好都判 False，
两半同时失效。存在 <256 的生产调用方（`react_public_updates.py:375`=192、
`completion_router.py:131`=150、`_tool_bridge_protocol.py:281`=180、
`_thread_state_auto_title.py:51`=60）。

边界：出厂 `data/custom_models.json` 今天不触发，需要运维新增一个不带该键的
reasoning 条目——也正是那段注释针对的中转场景。
连带发现：`custom_model_flags.py` 有两份实现，
`model_router/` 版严格、`platform/models/` 版对 OpenAI-compat 默认返回 True，
router 用的是严格那份，导致同一模型两处结论相反。

### P2-3 子代理线程行无 owner，陌生人可读/改名/枚举

`runtime/execution/subagents/threading.py:156-165` 写入的行 metadata 只有
lineage 字段，**没有 `owner_actor_id`/`tenant_id`**；
`thread_state_router.py:366` + `thread_access.py:240` 在 owner 缺失时 fallback
为放行。`require_auth=True` 下实测：陌生人对 alice 的**自有**线程 GET→404（网关有效），
但对这条无主行 GET state→200、POST rename→200、`/api/threads/search` 可枚举。

已收窄：验证者证明 `store.create` 自铸 `uuid4().hex`（`store.py:604`），
不接受传入 id，所以该行的 id **不等于** `binding.child_thread_id`，
真实子代理转录堆在另一个无 store 行的 id 下。因此这条无主行是**永久空壳**，
泄漏的是 lineage 元数据 + 角色标签 + 改名/枚举，**不是子代理转录内容**。
原报告"可公开分享他人子代理转录"经验证为**假**（POST share→409
`thread has no shareable messages`）。

### P2-4 人工 steer 以 `[子代理报告]` 开头会把线程写死

`frontend/src/core/threads/realtime-adapter.ts:451-456` 的过滤是
**按文本前缀**而非按 `source` 字段判断，`use-thread-stream-realtime.ts:1636`
配套。`turn/steer` 会沿用客户端 id（`_realtime_cerebrum_requests.py:103`），
`source` 默认 `"user"`。于是人工输入以该前缀开头时消息被当子代理报告过滤掉，
id 永不进 `acknowledgedClientMessageIds`，`delivery_state` 卡在 `"sending"`。

端到端复现（真 hook + renderHook）：`isLoading` 转 false 后仍 `sending`；
新消息 `startTurn` 调用 **0 次**，报 `Previous message is still pending`；
`RETRY_PENDING_MESSAGE_EVENT` 重试同样 0 次。只有切换线程（line 1174）能脱困。
现存测试 `realtime-adapter.test.ts:218` 只覆盖 `source: "subagent_report"`，
所以这个分支从没被钉住。
